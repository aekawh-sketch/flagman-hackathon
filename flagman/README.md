# Склад ресторана

Учёт поставок по партиям, сроки годности и FEFO, автоматический стоп-лист, горячие предложения
и защита от умышленных списаний. Решение кейса «Флагман» — полное ТЗ в [TZ.md](TZ.md).

## Что внутри

| Часть | Технологии |
|---|---|
| Бэкенд | Java 25, Spring Boot 4.1, PostgreSQL 16, Flyway, Spring Security, SSE, Swagger |
| Redis | сессии сотрудников (Spring Session), кеш меню, горячих предложений и прогноза, счётчики входа и запросов, события между серверами (Pub/Sub) — пакет `backend/src/main/java/ru/sphere/stock/redis` |
| Ядро предметной области | чистая Java без Spring и БД (`backend/src/main/java/ru/sphere/stock/domain`) — тот же код в продукте, симуляции и тестах |
| Интерфейс | React 19, TypeScript, Chakra UI 3, TanStack Query, Recharts, PWA |
| Виджет для сайта ресторана | `frontend/public/widget.js` — одна строка `<script>` |

## Запуск для разработки

Нужны Java 25, Node 22, PostgreSQL 16 и Redis 7+ (`brew install redis && brew services start redis`).
Без Redis — `SPRING_PROFILES_ACTIVE=no-redis`: кеш и счётчики в памяти процесса, как в программе для Windows.

```bash
createdb flagman && createdb flagman_test

cd backend && ./mvnw spring-boot:run       # API на :8080; при пустой базе — демо-данные за ~10 с
cd frontend && npm install && npm run dev  # интерфейс на :5173
```

Откройте http://localhost:5173 → «Демо-вход» → любая роль. Пароль демо-учёток — `demo1234`,
PIN: управляющий 2222, кладовщик 3333, повар 4444, кассир 5555, админ 1111.

- Swagger: http://localhost:8080/swagger-ui/index.html

Демо-ресторан — ИСТОК, точки `kush` («Истокград») и `kan` («Ясноречье»).

## Предприятия, поставки и просрочка (версия 2, ТЗ раздел 16)

- **Предприятия.** Каждое — сущность с ID; в каждой таблице данных есть `tenant_id`, ссылки на каталог составные
  `(tenant_id, id)` — у двух предприятий может быть свой `milk`, но база не даст смешать их данные. Учётка одна на систему,
  роль и точка — у членства: один человек работает в нескольких ресторанах. Приглашения — одноразовой ссылкой на 7 дней.
  Создать своё предприятие можно из меню профиля. Демо-предприятие — № 1 «ИСТОК».
- **Поставка** — формой в «Приёмке», файлом XML/JSON или `POST /api/{точка}/deliveries` (JSON или `application/xml`).
  Дата создания может быть в прошлом; в демо есть тестовая поставка, которая разрешает принять уже просроченное.
- **Приёмка частичная:** по строке факт от 0 и причина (недовоз, брак, просрочено, не заказывали). Просроченное без
  тестового флага принять нельзя.
- **Просрочку списывает человек.** Истёкшая партия сразу уходит из продаж и встаёт «под списание» (сигнал, кнопка на
  дашборде, панель в «Заявках на списание»). Автосписание системой — настройка `auto_writeoff_expired`, по умолчанию выключена.
- **«Поставлено — съедено — просрочено»** — в «Закупках» и «Аналитике»: что привезли, сколько съели, сколько пропало
  и сколько возить на поставку.

Пример XML-поставки:

```xml
<delivery id="SUP-42" number="П-42" createdAt="2026-10-11T08:00:00Z" supplier="ООО Ромашка">
  <line productId="milk" name="Молоко 3,2%" unit="ML" qty="10000" shelfLifeHours="72" costKop="90000"/>
</delivery>
```

Для проверок на копии базы: `API_TARGET=http://localhost:8081 npx vite --port 5174` — интерфейс ходит в другой экземпляр бэкенда.

## Подключение сайта ресторана

Сайт ресторана — внешняя система: ходит по ключу `X-Api-Key` с узкими правами (заказы, меню,
чтение склада и аналитики, поставки «на приёмку», живые события). Списания, приёмка и пересчёт
по ключу невозможны — только сотрудником с личным входом.

Для демо ключ сайта задаётся заранее, чтобы сервер сайта знал его и после сброса демо-данных:

```yaml
# backend/config/application.yml — не в git, Spring Boot читает его сам
stock:
  site-api-key: sk_istok_…        # то же значение — FLAGMAN_API_KEY в .env сайта
```

Сайт ИСТОК с сервером заказов — в соседней папке `../istok` (см. её README).
Портал поставщика «ФрешПоставка» — `../supplier` (`npm start`, :3002): шлёт поставки по API ключом
`stock.supplier-api-key` (одно право `deliveries:create`), видит итог приёмки.

## Программа для Windows

`desktop/` — склад программой для Windows, два режима (меню «Флагман», выбор — в `%APPDATA%\Flagman\settings.json`):
**с сервером** (по умолчанию) — окно Electron открывает склад на VPS, данные общие с телефоном и сайтом, сервер не ответил —
страница «Подключение к складу» (`desktop/connect.html`); **без сервера** — окно Electron, внутри PostgreSQL 16 и Java 25 для Windows, сервер сам отдаёт
интерфейс (`stock.web-dir`) и останавливается, когда окно закрыли (`stock.exit-on-stdin-close`). Собирается на маке:

```bash
cd desktop && npm install
node build.mjs            # → out/Flagman-win-x64.zip (Java и PostgreSQL скачиваются один раз в .cache)
```

Данные склада сборка не снимает сама: что лежит в `desktop/stage/seed/` (`flagman.dump` из `pg_dump -Fc --no-owner
--no-privileges` и папка `uploads`), то и развернётся при первом запуске. Пусто — программа создаст демо-ресторан.
Данные на Windows — в `C:\ProgramData\Flagman`, база слушает только `127.0.0.1:54329`. Инструкция для того, кто
запускает, — `desktop/win/README.txt`. В корне папки — `Flagman.exe` (запускатель `app\Flagman.exe`, исходник —
`desktop/win/launcher/launcher.c`), батники и README; сам Electron — в `app\`.

Сайт ИСТОК с кассой (`start-cafe.bat`, :3001) и портал поставщика (`start-supplier.bat`, :3002) едут в том же архиве
вместе с Node 22 — код из `../istok` и `../supplier` без `.env` и выгрузок заказов. Ключи к складу у каждого компьютера
свои: программа создаёт `keys.env` при первом запуске и передаёт складу (`SITE_API_KEY`, `SUPPLIER_API_KEY`), а склад
заводит ключ сайта и в базе, приехавшей дампом (`SeedService.connectSite`).

Проверка на маке без окон (своими PostgreSQL и Java, в пустой папке данных):

```bash
env -u ELECTRON_RUN_AS_NODE FLAGMAN_SMOKE=1 FLAGMAN_DATA=/tmp/flagman-test \
  FLAGMAN_PG_BIN=/opt/homebrew/bin FLAGMAN_JAVA=$(command -v java) npx electron .
```

## Сервер в интернете и Android-приложение

- **VPS:** `sh deploy/deploy.sh` — собрать backend и frontend и выкатить на `root@31.76.28.248` в `/opt/flagman`
  (Docker: PostgreSQL 16 + Redis 7 + сервер склада, который сам отдаёт интерфейс, + сайт ИСТОК с панелью ресторана из `../istok`).
  Склад — http://31.76.28.248:8085, сайт и касса — http://31.76.28.248:8086, портал поставщика — http://31.76.28.248:8087
  (ключи сайта и портала к складу — в `/opt/flagman/.env`).
  Пустая база → демо-ресторан; база, Redis и фото живут в томах Docker и переживают деплой. Пароли базы и Redis —
  в `/opt/flagman/.env`, их создаёт деплой.
- **Android:** `android/` — WebView на Java (APK ≈ 1,2 МБ, Android 8+). `sh android/build-apk.sh [адрес]` →
  `android/Flagman.apk`. В приложении: сканер QR этикеток (кнопка в шапке — только в приложении: сканер Google из
  сервисов Play, текст QR приходит странице событием `flagman:qr`, открывается карточка партии), фото с камеры для
  списаний и приёмки, сохранение файлов в «Загрузки», «Режим киоска», экран «Нет связи». Адрес склада меняется без пересборки: долгое нажатие на иконку → «Адрес сервера».
  Ключ подписи — `android/keystore/` (не в git): обновление ставится поверх, только если подписано тем же ключом.
  Печать с телефона не поддерживается — window.print в WebView не работает.

## Тесты

```bash
cd backend && ./mvnw test
```

- ядро: FEFO, окна сроков, вскрытие, брутто/нетто, сеты, заказ «всё или ничего», стоп-лист, прогнозы, заготовки, горячие предложения;
- интеграционные на настоящей БД: 50 параллельных заказов на последние порции, идемпотентность, отказ без побочных эффектов,
  возврат при отмене, журнал только на добавление и обнаружение подделки, правила ручного списания, изоляция предприятий,
  приглашения, частичная приёмка, XML и защита от XXE, списание просрочки человеком, отчёт по поставкам;
- Redis на настоящем сервере Redis: меню из кеша до изменения склада или истечения срока, изменение на другом сервере
  видно через версию склада, блокировка после 5 неверных паролей, события через Pub/Sub, сессия в Redis, ответ 429.

## Демо за 5 минут

1. Войдите админом → «Демо-панель» → скорость ×600.
2. Сценарий «Поставка с коротким сроком» → «Горячие предложения» объясняют, что продвигать и почему.
3. Сценарий «Дефицит лосося» → «Касса»: блюда с лососем в стопе, заказ сверх остатка — отказ с объяснением и альтернативами.
4. Сценарий «Подозрительный сотрудник» → «Подозрительное»: аномалии A2/A4, заявка ждёт подписи.
5. «Журнал» → «Проверить целостность»: хэш-цепочка цела.
